Section 01

Project Background & Why We Test

The Forsys production website is a pure static HTML/CSS/JavaScript site hosted via FTP. It has no build pipeline, no component framework, and no automated tests. Any change to a shared CSS file — for example, base.css, which controls the navigation bar, footer, and global tokens — immediately affects every single page on the site.

Before this test suite existed, there was no safety net. A developer could change a color variable or a layout rule in base.css, push to main, and the FTP deploy would ship it to production seconds later — without any automated check confirming the change looked correct on every page. The only way to catch a regression was manual visual inspection, which is unreliable and time-consuming across 78 pages.

The Core Problem

When you have a shared stylesheet, the blast radius of any change is the entire site. Consider these realistic scenarios:

  • A padding change in the nav causes the logo to be cut off on mobile screens.
  • A z-index change makes the mega-menu appear behind page content on certain pages.
  • A font-weight change in a headline class causes text to reflow and overlap the CTA button.
  • A hero background color token is updated and accidentally applied to a section it was not intended for.
  • A new page is pushed with a missing CSS import, causing it to render unstyled.

All of the above are invisible to a developer looking only at the file they edited. They require looking at the live rendered output across all affected pages, at all screen sizes. Manual inspection at that scale is not realistic.

The Solution

A visual regression test suite that automatically screenshots every production page at every screen size on every pull request, and blocks the merge if any screenshot differs unexpectedly from the approved baseline. No regression can ship without being seen first.

Section 02

What is Visual Snapshot Testing

Visual snapshot testing is a technique where a test runner opens a page in a real browser, takes a screenshot, and compares that screenshot pixel-by-pixel against a pre-approved reference image called a baseline. If the current screenshot matches the baseline within a defined tolerance, the test passes. If it differs beyond that tolerance, the test fails and reports exactly which pixels changed.

The key word is regression. This type of testing is not about checking whether a page is "correct" in an abstract sense — it is about detecting unintended changes from a known-good state. The baseline represents the state you approved. Any deviation is a signal that something changed.

2.1 How it Works — Step by Step

  1. Server starts. Playwright launches a local static file server (npx serve . --listen 3000) that serves the entire production folder at http://localhost:3000. This means every test runs against the exact same files that are deployed to production — not a separate build or transformed output.
  2. Browser opens the page. Playwright launches a headless Chromium browser and navigates to the page URL. It waits until waitUntil: 'load' — meaning the browser has fired the load event, which only happens after all stylesheets, scripts, and images referenced in the HTML have finished downloading. This guarantees the page is fully rendered before the screenshot is taken.
  3. CSS stabilisation is injected. A JavaScript snippet injects a <style> tag into the page that freezes all animations and transitions to 0s duration and hides the scrollbar. This ensures the screenshot is deterministic — it looks the same every time regardless of timing or scroll state.
  4. Screenshot is taken. Playwright captures the current browser viewport (what is visible without scrolling) as a PNG image.
  5. Comparison against baseline. The new screenshot is compared against the stored baseline PNG. If no baseline exists yet (first run), Playwright saves the screenshot as the new baseline. If a baseline exists, it computes the difference.
  6. Pass or fail. If the percentage of differing pixels exceeds maxDiffPixelRatio: 0.07 (7% of all pixels), the test fails. Playwright generates a diff image showing the exact regions that changed, highlighted in red.

2.2 What It Catches vs What It Does Not Catch

✅ Will catch

  • CSS color changes on nav, hero, or any above-fold element
  • Layout shifts — elements moving position
  • Text reflow caused by font or size changes
  • Missing CSS — page renders unstyled
  • Elements disappearing or appearing unexpectedly
  • Overlapping elements caused by z-index or overflow changes
  • Wrong logo, missing logo
  • Nav or hero broken on mobile layout
  • Viewport-level padding/margin changes

❌ Will not catch

  • JavaScript interaction bugs (clicks, hover states, animations)
  • Form validation logic
  • Broken hyperlinks
  • Content changes below the visible fold
  • SEO metadata (title, description tags)
  • Accessibility tree (screen reader content)
  • API or backend responses
  • Page load performance
  • Console errors

2.3 Why Playwright Was Chosen

Several tools exist for visual snapshot testing (Percy, Chromatic, BackstopJS, Cypress). Playwright was selected for the following reasons:

Section 03

Scope — Why Viewport-Only Screenshots

A critical design decision was made early: take viewport-only screenshots (what is visible in the browser without scrolling) rather than full-page screenshots (the entire page height). This was not a compromise — it was the correct engineering choice, and here is the full reasoning.

The Full-Page Problem

The Forsys website uses a scroll-fade animation pattern. Cards and sections below the fold have opacity: 0 and transform: translateY(20px) applied to them by JavaScript as the page loads, using the browser's IntersectionObserver API. These elements only become visible when the user scrolls them into the viewport.

When Playwright takes a full-page screenshot, it captures the entire page DOM without scrolling. The IntersectionObserver never fires for below-fold elements because they were never scrolled into view. The result is a screenshot where half the page content is invisible — showing only blank spaces where the cards should be.

You could work around this by injecting CSS to force opacity: 1 on all elements, but this creates a different problem: the screenshot no longer reflects what a real user sees. It becomes an artificial view of the page that does not match any real rendering state.

Why the Viewport Is the Right Target

The viewport — the nav and hero section — is the highest-risk, highest-value area to test for several reasons:

  • It is the first thing every visitor sees. A broken nav or a misrendered hero is a critical failure. A slightly shifted card three sections below the fold is minor.
  • It is driven entirely by shared CSS. The nav comes from base.css. The hero section uses shared tokens and shared component classes. Any global CSS change directly affects this region.
  • It is stable. The viewport content is static — no scroll-dependent visibility, no lazy-loaded images entering frame, no intersection-triggered state changes. This makes screenshots deterministic and comparable between runs.
  • It is the correct scope for regression detection. Each page has a distinct hero design (different background, headline, CTA layout). If a CSS change breaks the hero on a services page differently than on a solutions page, both will be caught because both pages are in the test suite.
💡
Industry Principle — Narrowing the Scope

In professional QA, this approach is called "scoping the snapshot to the stable region." You define what region of the UI is the authoritative test target — the part that is both high-value and low-noise — and you snapshot only that. Full-page snapshots of complex, dynamic pages create test suites that break constantly due to unrelated content changes, producing alert fatigue where engineers start ignoring failures.

Section 05

Viewports and Devices

Playwright is configured with three projects, each representing a viewport size and device type. A project is essentially a named configuration that says "run all tests in this browser with these dimensions." The same test file runs once per active project, meaning 78 tests × 2 active projects = 156 total test runs.

Project NameDevice ProfileResolutionStatusReason
Desktop Desktop Chrome 1280 × 720 Active Standard laptop screen — the primary layout target for the site
Tablet Desktop Chrome 1024 × 768 Skipped Tablet layout is covered by Desktop + Mobile breakpoints. No unique design decisions at 1024px that aren't already caught by the adjacent viewports
Mobile Pixel 5 375 × 812 Active Represents the smallest common mobile screen. The mobile nav (hamburger), stacked hero, and responsive card layouts are all tested at this width

Why 1280px for Desktop

1280px is the most common laptop screen width and the standard "desktop" breakpoint used in the Forsys CSS design system (≥1025px = desktop). It is wide enough to show the full nav, mega-menus, and hero layout without triggering any responsive overrides.

Why 375px for Mobile

375px is the viewport width of an iPhone SE, iPhone 12/13/14, and similar small Android devices. It represents the minimum viable mobile width. If the layout works at 375px, it works on essentially all modern mobile devices. The Pixel 5 device profile also sets the correct user-agent string so any browser detection JavaScript behaves as it would on a real mobile device.

Why Tablet is Skipped

The Forsys CSS uses three breakpoints: desktop (≥1025px), tablet (≤1024px), and mobile (≤768px). The tablet breakpoint at 1024px sits between the Desktop and Mobile test viewports. In practice, the layout at 1024px is a slight variation of desktop — the nav switches to a hamburger menu but the content columns remain largely the same. Running Tablet tests would add 78 more test cases but catch very few regressions that Desktop and Mobile do not already catch. Skipping Tablet halves the test count without meaningful reduction in coverage quality.

ℹ
Tablet can be re-enabled at any time

If the design ever introduces tablet-specific layouts that differ significantly from both Desktop and Mobile, remove the test.skip line from the beforeEach hook in snapshots.spec.js and regenerate baselines. The project configuration for Tablet already exists in playwright.config.js.

6.1 playwright.config.js — Every Setting Explained

playwright.config.js
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',           // Where Playwright looks for test files
  retries: process.env.CI ? 1 : 0,   // 1 retry in CI, 0 locally
  workers: process.env.CI ? 4 : undefined,  // 4 parallel workers in CI

  reporter: [
    ['html', { outputFolder: 'playwright-report', open: 'never' }],
    ['list']
  ],

  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },

  expect: {
    toHaveScreenshot: {
      maxDiffPixelRatio: 0.07,   // 7% pixel diff tolerance
    },
  },

  webServer: {
    command: 'npx serve . --listen 3000',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
    timeout: 30000,
  },

  projects: [...]
});
SettingValueDetailed Explanation
testDir ./tests Playwright recursively scans this directory for any file matching *.spec.js. All test files live under tests/ so this catches everything including future test files added to subdirectories.
retries CI: 1, Local: 0 On CI, a failed test gets one automatic retry before being marked as failed. This absorbs transient rendering glitches (occasional GPU or font rendering variance) without masking real failures. Locally, no retries so feedback is instant.
workers CI: 4, Local: auto Number of test workers running in parallel. 4 workers in CI means up to 4 tests run simultaneously, cutting the total CI time to roughly 25% of sequential time. Locally, undefined tells Playwright to use half the available CPU cores automatically.
reporter: html open: 'never' Generates a full HTML report with pass/fail summary, screenshots, diffs, and timings. open: 'never' prevents the browser from auto-opening the report (which would hang CI). The report is uploaded as a GitHub Actions artifact and available for 7 days.
reporter: list — Prints a real-time list of each test as it runs to the terminal. Useful for monitoring CI logs live.
baseURL http://localhost:3000 All URLs in tests are relative (/index.html). Playwright prepends this base URL, so /index.html becomes http://localhost:3000/index.html.
trace on-first-retry Captures a full execution trace (network requests, DOM snapshots, screenshots at each action, console logs) on the retry run. If a test fails twice, the trace is available in the HTML report for deep debugging.
screenshot only-on-failure In addition to snapshot comparison screenshots, Playwright takes a "failure screenshot" when a test fails. This is separate from the diff — it shows the actual rendered state at the moment of failure.
maxDiffPixelRatio 0.07 Up to 7% of the total pixel count may differ before a test fails. A 1280×720 viewport has 921,600 pixels — 7% allows up to 64,512 pixels to differ. This threshold was calibrated by observing that font anti-aliasing differences between Windows 11 local and Windows Server CI caused ~3–5% pixel variance on text-heavy pages.
webServer.command npx serve . --listen 3000 Starts a static file server from the project root before any tests run. serve is in devDependencies so npm ci installs it — it never needs to be downloaded on the fly during CI.
reuseExistingServer !CI → true locally Locally, if port 3000 is already in use (you started serve manually), Playwright reuses it instead of trying to start another instance. On CI, always starts fresh.
webServer.timeout 30000ms Playwright waits up to 30 seconds for the server to respond before failing. This gives enough time for serve to start on CI even if the system is under load.

6.2 The Test File — snapshots.spec.js

The test file is intentionally simple. It does not contain any complex logic — just a loop that generates one test per page. This is deliberate: visual snapshot tests should be mechanical and predictable. The logic is in the configuration, not the test code.

tests/visual/snapshots.spec.js — core loop
for (const { name, url } of PAGES) {
  test(name, async ({ page }) => {
    await page.goto(url, { waitUntil: 'load' });
    await prepPage(page);
    await expect(page).toHaveScreenshot(`${name}.png`);
  });
}

Each iteration creates a named Playwright test. The test name is the name field from the PAGES array (e.g., services-revenue-lifecycle-strategy). The baseline PNG filename is derived from this name plus the project name — for example, services-revenue-lifecycle-strategy-Desktop.png.

waitUntil: 'load' is specifically important. The alternative, domcontentloaded, fires as soon as the HTML is parsed — before stylesheets have finished downloading. Screenshots taken at domcontentloaded showed blank pages for some pages in CI because the CSS had not loaded yet. 'load' waits for all linked resources (CSS, fonts, images) to finish.

6.3 prepPage() — Why It Exists

After navigation and before the screenshot, the prepPage() function injects a CSS override tag into the live page. This CSS is never saved to disk — it only exists in the browser's memory for the duration of the test.

prepPage() — injected CSS
async function prepPage(page) {
  await page.addStyleTag({
    content: `
      *, *::before, *::after {
        animation-duration: 0s !important;
        animation-delay: 0s !important;
        transition-duration: 0s !important;
        transition-delay: 0s !important;
      }
      ::-webkit-scrollbar { display: none !important; }
      html { scrollbar-width: none !important; }
    `,
  });
}
RuleWhy It Is Needed
animation-duration: 0s CSS keyframe animations (loading spinners, fade-ins, pulse effects) run on a timer. If a screenshot is taken mid-animation, the element is in a transitional state that differs from the baseline. Setting duration to 0 forces all animations to their end state instantly.
animation-delay: 0s Some animations are delayed to stagger their entrance. A delayed animation means the element may still be at opacity 0 or off-screen when the screenshot fires. Zeroing the delay ensures all animated elements are visible immediately.
transition-duration: 0s CSS transitions on hover states, nav dropdowns, and button effects can leave elements mid-transition if triggered by page load scripts. Zero duration snaps all transitions to their resolved state.
transition-delay: 0s Same reason as animation-delay — prevents staggered transitions from leaving elements in a pre-transition state.
::-webkit-scrollbar { display: none } On headed (non-headless) Chrome, a scrollbar renders on the right edge of the viewport. This scrollbar occupies approximately 15px of width, making the effective content area 1265px instead of 1280px. This caused every test to fail with 100% of pixels different due to layout reflow. Hiding the scrollbar normalises the viewport width between headed and headless modes.
scrollbar-width: none Firefox scrollbar equivalent — ensures consistent behaviour across browsers even though Chromium is the primary test browser.
⚠
This CSS does not affect your live site

page.addStyleTag() injects styles only into the browser's in-memory DOM during the test run. It does not write to any file. The moment the browser closes after the test, the injection is gone. Your site files are never touched.

Section 07

Baseline PNG Management

7.1 Where Baselines Are Stored

Playwright stores baseline PNGs in a folder named after the test file, suffixed with -snapshots:

tests/ visual/ snapshots.spec.js snapshots.spec.js-snapshots/ homepage-Desktop.png homepage-Mobile.png services-revenue-lifecycle-strategy-Desktop.png services-revenue-lifecycle-strategy-Mobile.png ... (156 PNG files total)

These PNGs are committed to the git repository. This is intentional and important — the baselines need to be version-controlled alongside the code. When a PR is opened, CI checks out the branch (which includes the current baselines from that branch) and compares screenshots against those baselines. The baselines travel with the code.

Each PNG filename encodes three pieces of information: the page name, the project (viewport), and implicitly the platform (Windows, because baselines were generated on windows-latest).

7.2 Why CI Generates Baselines, Not the Local Machine

This is the most important operational detail in the entire test suite. Font rendering on Windows 11 (local developer machine) differs from font rendering on Windows Server (GitHub Actions windows-latest runner) due to differences in:

  • ClearType settings — the sub-pixel font smoothing algorithm differs between consumer Windows 11 and Windows Server 2022
  • GPU rendering path — developer machines use a physical GPU for rendering; CI runners use software rendering (WARP)
  • DPI scaling — developer machines may have DPI scaling applied; CI runners run at 96 DPI
  • Font hinting — the degree of font hinting applied to render sharp characters differs between environments

These differences cause text-heavy sections to differ by 3–5% in pixel values even when the layout is identical. If baselines are generated locally and CI compares against them, text pixels will almost always fall outside the tolerance threshold, causing false failures on every run.

The solution is to generate baselines on the same environment that runs the tests. The update-snapshots.yml workflow runs on windows-latest and regenerates all baselines in that environment. CI also runs on windows-latest. Both use the same rendering path — comparisons are always apples-to-apples.

✓
Rule: always regenerate baselines using the GitHub Actions workflow

Never run --update-snapshots locally and commit the resulting PNGs. Those PNGs will fail on CI due to environment rendering differences. Always use the Update Visual Snapshots GitHub Actions workflow.

7.3 When to Regenerate Baselines

ScenarioAction RequiredHow
Intentional design change (new color, layout update) Regenerate baselines to accept the new design as correct Run Update Visual Snapshots workflow from Actions tab
New page added to the site Add the page to the PAGES array, then regenerate Edit snapshots.spec.js, push, run workflow
Page removed from the site Remove from PAGES array and delete old PNG files Edit snapshots.spec.js, delete orphan PNGs, push
A test is failing due to an accidental regression Fix the regression — do NOT regenerate baselines to hide it Find and revert the CSS/HTML change that caused the diff
All tests fail after switching CI runner OS Regenerate baselines on new OS Run workflow after updating runs-on in ci.yml
Section 08

CI/CD Pipeline

Three GitHub Actions workflows exist in .github/workflows/. Two are part of the test suite; one is the existing deployment workflow that was not modified.

8.1 ci.yml — Automatic on PR and Push

.github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: windows-latest

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - name: Install dependencies
        run: npm ci
      - name: Install Playwright browsers
        run: npx playwright install --with-deps chromium
      - name: Run tests
        run: npx playwright test
      - name: Upload test report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7
StepWhat It DoesWhy
Trigger: pull_request Runs when a PR is opened, updated, or re-opened against main This is the primary gate — tests must pass before a merge is allowed. Branch protection requires this check to pass.
Trigger: push to main Runs again after a PR is merged to main Post-merge verification. Confirms the merged state of main is clean. Also triggers the FTP deploy.
runs-on: windows-latest Uses a Windows Server 2022 runner Must match the OS used to generate baselines. Windows is used instead of ubuntu-latest because font rendering on Linux differs from Windows. The site is developed on Windows so Windows CI gives the most accurate comparison.
actions/checkout@v4 Checks out the repository code Gives the runner access to all files including the baseline PNGs in tests/visual/snapshots.spec.js-snapshots/.
setup-node + cache: npm Installs Node 20, caches the npm cache between runs Caching means npm ci only downloads packages when package-lock.json changes — saves ~30 seconds on most runs.
npm ci Installs exact versions from package-lock.json Unlike npm install, npm ci never modifies package-lock.json — it fails if there is a mismatch. Ensures reproducible installs. Also installs serve from devDependencies so it is available without downloading at test time.
playwright install --with-deps chromium Downloads the Chromium browser binary + OS dependencies Playwright bundles its own browser — it does not use whatever Chrome is installed on the system. --with-deps installs required system libraries (font rendering, GPU libs) that the headless browser needs on Windows Server.
npx playwright test Runs all tests with 4 workers, 1 retry on failure This is the main event. Runs all 156 snapshot tests in parallel. The job exits with code 1 if any test fails after retries, which marks the GitHub Check as failed.
upload-artifact (if: always()) Uploads the HTML report regardless of pass/fail if: always() ensures the report is uploaded even when tests fail — which is exactly when you need it most. The report is available in the Actions tab under "Artifacts" for 7 days.

          cache: 'npm'
      - name: Install dependencies
        run: npm ci
      - name: Install Playwright browsers
        run: npx playwright install --with-deps chromium
      - name: Regenerate snapshots
        run: npx playwright test tests/visual --update-snapshots
      - name: Commit updated snapshots
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add tests/visual/snapshots.spec.js-snapshots/
          git diff --staged --quiet || git commit -m "chore: update visual snapshot baselines"
          git push

workflow_dispatch means this workflow can only be started manually from the GitHub Actions tab. It never runs automatically. This is intentional — regenerating baselines is an intentional human decision, not something that should happen automatically on every push.

The last step uses git diff --staged --quiet || git commit. This is a safety check: if the baselines did not change (no visual difference detected), it skips the commit rather than creating an empty commit. The || means "if the diff is NOT quiet (i.e., there are changes), then commit."

Its trigger (push to main) means it runs after a PR is merged and CI passes — the deploy only happens after tests have confirmed the code is safe.

Section 09

Branch Protection Rules

Branch protection is configured using GitHub Rulesets (the modern replacement for the classic Branch Protection Rules). A Ruleset applies to the main branch and enforces the following rules. Crucially, the bypass list is empty — nobody, including repository admins, can bypass these rules.

RuleSettingEffect
Require a pull request before merging Enabled — 0 required approvals Nobody can push directly to main. All changes must come through a PR. 0 approvals means the PR author can merge their own PR without waiting for someone else — but they still cannot bypass the test check.
Required status checks test (from ci.yml) must pass The merge button is disabled until the test job in ci.yml reports success. This is the core enforcement mechanism — tests must pass before code can enter main.
Block force pushes Enabled Even users with admin access cannot use git push --force to overwrite main branch history. Prevents accidental or intentional history rewriting.
Require conversation resolution Enabled Any review comment left on a PR must be marked as resolved before the PR can be merged. Prevents open questions or unaddressed feedback from being merged.
Bypass list Empty No user or role is exempt from any of the above rules. Admin must also open a PR, pass all tests, and merge normally.

Why 0 Required Approvals

Requiring 1 approval means every PR — including admin's own PRs — would need someone else to review and approve it. For a small team where the admin frequently pushes changes, this creates unnecessary friction. The protection value comes from the test check, not peer review. 0 approvals keeps the flow smooth while still enforcing all automated checks. If the team grows and peer review becomes important, this can be raised to 1.

If any of the 156 tests fail, the merge button on GitHub displays "Required status check 'test' has not passed" and is disabled. The PR author must investigate the failure, fix the code, and push an update. CI re-runs on the updated push and, if tests now pass, the merge button becomes active.

What Happens When a Test Fails

  1. Go to the PR on GitHub. Click the "Details" link next to the failed test check.
  2. In the Actions run, download the playwright-report artifact. Open index.html in the report folder.
  3. Find the failing test. The report shows the test name, the actual screenshot, the baseline screenshot, and a diff image with the changed regions highlighted in red.
  4. Determine if the change was intentional or accidental.
    • If accidental (a CSS regression): find and revert the change, push again.
    • If intentional (a redesign): merge the PR, then run the Update Visual Snapshots workflow to update baselines.
Section 10

Day-to-Day Developer Workflow

Making a Routine Change (bug fix, content update)

  1. Create a new branch: git checkout -b fix/nav-padding
  2. Make your changes to HTML/CSS files
  3. Optionally run tests locally first: npx playwright test tests/visual
  4. Commit and push: git push origin fix/nav-padding
  5. Open a pull request on GitHub against main
  6. CI runs automatically — wait for the green check
  7. If tests pass: merge the PR. FTP deploy runs automatically.
  8. If tests fail: review the diff in the HTML report, fix the issue, push again

Making an Intentional Design Change

  1. Create a branch, make the design changes, push and open a PR
  2. CI runs — tests will fail because the new design differs from baselines (expected)
  3. Review the diffs in the report — confirm the changes look correct and intentional
  4. Merge the PR (the tests will still show as failed — this is the one exception where you merge with a failure)
  5. Go to GitHub Actions tab → Update Visual Snapshots → Run workflow
  6. The workflow regenerates all 156 baseline PNGs from the new design and commits them to main
  7. Future PRs will now be compared against the updated baselines
⚠
Merging with failed tests — when is it acceptable?

Only when you are certain the failures are caused by an intentional design change that you have reviewed and approved. Never merge with failures from an unreviewed or unknown cause. When in doubt, investigate first.

Adding a New Page to the Site

  1. Create the HTML file in the appropriate folder
  2. Open tests/visual/snapshots.spec.js
  3. Add a new entry to the PAGES array in the correct group section
  4. Push and open a PR — CI will fail because no baseline PNG exists yet for the new page
  5. Merge the PR
  6. Run the Update Visual Snapshots workflow — it generates the baseline for the new page
  7. Subsequent CI runs will now include the new page in comparisons

Removing a Page from the Site

  1. Delete the HTML file
  2. Remove the corresponding entry from the PAGES array in snapshots.spec.js
  3. Delete the two orphaned PNG files from tests/visual/snapshots.spec.js-snapshots/ (Desktop and Mobile)
  4. Commit all three changes together and push as a PR

Commands Reference

CommandWhat It DoesWhen to Use
npx playwright test Runs the full test suite (all 156 tests, all projects) Final check before pushing. Uses all CPU cores locally.
npx playwright test tests/visual Runs only the visual snapshot tests During development when you only need to check visuals. Faster than running the full suite if other test types are added later.
npx playwright test --headed Runs tests in a visible Chrome window Debugging — you can watch the browser navigate each page. Slower but useful for seeing exactly what Playwright sees.
npx playwright test tests/visual --update-snapshots Regenerates baseline PNGs from current page state Only use locally for exploration. Always use the GitHub Actions workflow for official baselines.
npx playwright show-report Opens the HTML report in the browser After running tests locally — review pass/fail results, diffs, and screenshots.
npx playwright test --grep "homepage" Runs only tests whose name contains "homepage" When you only want to test a single page. Combine with --headed for quick debugging of one page.
npx playwright test --project=Desktop Runs only the Desktop project (skips Mobile) When you only care about desktop layout. Halves the number of tests.
npx playwright test --project=Mobile Runs only the Mobile project When debugging a mobile-specific layout issue.
npx playwright test --workers=1 Runs tests sequentially (no parallelism) When debugging — parallel tests can interleave their output making it hard to read. Sequential is easier to follow.
npx playwright test --timeout=60000 Sets a 60 second per-test timeout When testing on a slow machine or network — prevents false timeouts.
Section 12

Troubleshooting Guide

SymptomRoot CauseFix
All tests fail with 100% pixel difference Baselines were generated on a different OS or environment Run the Update Visual Snapshots GitHub Actions workflow to regenerate baselines on windows-latest
Screenshot shows a blank/white page CSS did not load before screenshot — waitUntil may be wrong, or the server did not start in time Confirm waitUntil: 'load' is set. Check that serve is in devDependencies in package.json so npm ci installs it. Increase webServer.timeout if server starts slowly.
All tests fail with a 15px width shift Test was run in headed mode without scrollbar CSS, or prepPage() was not called Confirm prepPage(page) is called after navigation in the test. The scrollbar-hiding CSS must be injected before the screenshot.
One specific page fails consistently That page has an animation, dynamic content, or a different layout that was changed Run with --grep "page-name" --headed and watch what renders. If it's a real regression, fix the CSS. If it's an intentional change, regenerate baselines.
Tests pass locally but fail on CI Font rendering difference between local Windows 11 and CI Windows Server Never use locally-generated baselines for CI comparison. Run the Update Visual Snapshots workflow to generate CI-compatible baselines.
CI times out waiting for web server serve is not installed and npm is trying to download it during the test run Confirm "serve": "^14.2.6" is in devDependencies in package.json. Run npm install locally, commit the updated package-lock.json.
CI check passes but merge button is still disabled The status check name in the Ruleset does not match the job name in ci.yml In GitHub Ruleset settings, the required status check must be exactly test (matching the job name jobs: test: in ci.yml).
update-snapshots workflow fails with "nothing to commit" No visual changes were detected — baselines are already up to date This is not an error. The git diff --staged --quiet || guard prevents an empty commit. The workflow completes successfully without committing.
Flaky test — fails occasionally with no code changes Transient rendering variance (slight font or GPU rendering difference between runs) The retries: 1 in CI configuration handles most transient failures automatically. If a test is persistently flaky, consider increasing maxDiffPixelRatio slightly for that page, or investigate if there is dynamic content (date/time) rendering in the hero.
New page test fails with "missing baseline" A page was added to PAGES array but baselines have not been generated yet Run the Update Visual Snapshots workflow after adding the page. The workflow generates the new baseline PNG and commits it.
Push directly to main is rejected Branch protection Ruleset blocks direct pushes to main This is expected and correct. Create a branch, push to the branch, open a PR. Nobody can push directly to main — including admins.

GitHub Actions Cost

GitHub Actions bills by the minute for private repositories. The billing rate for windows-latest runners is 2× the base rate compared to Linux runners — so 10 minutes of Windows CI = 20 billed minutes.

Repo VisibilityFree MinutesEffective Free BudgetImpact
Public Unlimited Unlimited No cost
Private 2,000 Linux min/month ~1,000 Windows min/month (2× multiplier) ~100 PR runs/month before charges

The repository is currently public, so CI runs are entirely free regardless of volume. If the repository is made private in the future, 100 PR runs per month on the free tier is generous for a website project.

Storage

156 PNG files at approximately 50–150 KB each = roughly 10–25 MB of baseline images stored in the git repository. This is negligible. Git stores binary files efficiently using delta compression — unchanged PNGs take very little space in git history.
